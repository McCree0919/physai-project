# Layer 3：分层控制设计（主线）

状态：设计稿，待确认；本文件只写设计，不含代码。分支layer3。
【数据】为已有测量或源码支持的结论，附出处；【推断】为设计判断，注明验证方法。

## 0. 为什么转为分层

- 【数据】端到端PPO（无记忆，6连续+2离散）：
  - 目标表示实验3000万步，RewardProgress始终为0（[LAYER3_TARGET_REPRESENTATION.md](LAYER3_TARGET_REPRESENTATION.md)）。
  - 示范状态初始化2种子×5M：地面起点一级登层率为0；S2的一级与零动作基线持平（97%）；S1b→一级、S3→二级没有学会（[LAYER3_DEMO_INIT.md](LAYER3_DEMO_INIT.md)）。
- 【数据】脚本控制器能完成同一身体、同一物理下的任务：
  - 单Tall箱16/16，两级台阶16/16（[BOX_STACK_ACCEPTANCE.md](BOX_STACK_ACCEPTANCE.md)）。
  - 横档墙扫描1040次中成功934次（[LAYER2_SOLVABILITY.md](LAYER2_SOLVABILITY.md)）。
- 【推断】瓶颈在长时序的运动探索，不在"选哪条路"。分层的做法：
  - 把运动执行交给可验证的通用执行器；
  - 强化学习只负责路线选择，即在玩家结构上"下一步抓哪条边"。
  - 端到端线作为次要线保留（[LAYER3_HEIGHT_SHAPING.md](LAYER3_HEIGHT_SHAPING.md)）。

## 1. 总体结构

```
高层策略（PPO，离散K选1，带动作遮罩，事件触发决策）
   │ 选择候选顶边 e_k
   ▼
底层执行器（脚本化，参数=目标顶边几何）
   伸手 → 抓握 → 拉升 → 翻越/悬挂换手 → 站稳/挂稳
   │ 返回 {结果类型, 用时, 新支撑}
   ▼
身体（不改）：只调用 SetHandTarget / SetGrab，与现有Agent接口相同
```

- 一个高层"步"是一个option，即执行器的一次完整尝试，属于半马尔可夫决策。
- 决策时机：执行器报告结束（成功或失败）时，调用`Agent.RequestDecision()`。不用固定周期的DecisionRequester。
  - 【数据】ML-Agents 4.0.0支持按需决策（`Agent.RequestDecision`，`Library/PackageCache/com.unity.ml-agents@592fae96fab2/Runtime/Agent.cs:855`）。
  - 【数据】也支持离散动作遮罩（`IDiscreteActionMask.SetActionEnabled`，`Runtime/Actuators/IDiscreteActionMask.cs:24`，在`WriteDiscreteActionMask`中写入）。
- 物理、身体参数、ProjectSettings不变。执行器与现有专家一样，只使用公开接口。

## 2. 高层：候选顶边与策略接口

### 2.1 从几何自动提取候选顶边

输入为场地内所有带`ClimberSurface`的静态`BoxCollider`，即玩家结构加载后的同一批物体，不读结构JSON的语义标签。步骤如下。

1. **顶面**：在箱子局部坐标中找出法线与场地up夹角≤45°的面。判据与`ClimberSurface.TopPoint`和身体的`NotTop`规则相同（`ClimberBody.cs:153`）。箱子局部坐标可以处理任意yaw，例如玩家旋转的Wide。
2. **边段**：顶面的4条边，各按0.05m间隔采样。每个采样点用身体实际使用的`GripClearance.IsClear`判断净空（半径0.10m、高0.22m的胶囊）。连续可抓的采样合并为区间，长度<0.30m的区间丢弃。
   - 这样候选与身体的真实抓握合法性一致。不使用`BoxStackGeometry.Edges`的中点盒抽样，它只是保守的特征统计。
3. **唇沿判定**：沿外法线方向偏移0.15m向下投射。落差≥0.25m的才是"唇沿"（lip）。
   - 落差小的是平接缝，例如两个等高箱相邻处。平接缝是可以走过去的平台内部，不作为目标。
4. **可站深度**：沿内法线方向，从边向顶面内部做5点支撑投射，与`ClimberAgent.TrySupport`使用同一套采样（躯干足印约0.6×0.35m）。
   - 记录从边起连续可站的深度d_stand。
   - 据此给边打类型标签：`mantle`（d_stand≥0.45m，可翻上去站住）或`hang`（只能悬挂，用于换手过渡）。
5. **当前可达过滤**：相对当前支撑（站立面或抓住的边）计算：
   - 竖直升高Δh；
   - 水平距离ρ；
   - 外法线与躯干朝向的夹角ψ；
   - 从肩部到采样点的遮挡射线是否被阻挡。
   - 阈值Δh_max、ρ_max、ψ_max不预先拍定，由第4节阶段B的执行器标定实验确定（成功率≥80%的区域）。
   - 【数据】现有的唯一参考：横档墙在高差0.35–0.60m、全部横距下8/8（[LAYER2_SOLVABILITY.md](LAYER2_SOLVABILITY.md)），单Tall箱从地面上升1.0m为16/16。
6. **排序与上限**：保留K=8个候选，按（Δh降序，|ψ|升序，区间中心x）确定性排序，不足的用遮罩填充。排序只为让槽位稳定，不编码任何路线偏好。

### 2.2 观察（建议约100维，固定长度）

| 内容 | 维度 | 说明 |
|---|---:|---|
| 本体摘要 | 10 | 当前支撑类型（站立/悬挂/无）one-hot 3；支撑面高度相对躯干1；躯干速度3；剩余时间比例1；已用option数/上限1；上一option结果类型1 |
| 目标信标 | 3 | 目标中心相对躯干，与现有Agent相同（除以6m） |
| 每候选 ×8 | 8×11 | 存在1；边中点相对躯干3；外法线水平方向2；区间长度1；Δh 1；类型mantle/hang 1；d_stand 1；从该边到目标信标的相对高差1 |
| 历史 | 2 | 该候选在本回合已失败次数（按槽位对应的边ID），用于避免反复选同一条失败边 |

- 坐标与现有Agent相同：躯干局部坐标，不含绝对坐标、结构ID或难度标签。
- 可选消融：附加现有的5×5高度图（100维，`ClimberAgent.BuildObservations`中的同一套采样），检验"只看候选列表"是否丢失了路线所需的信息。

### 2.3 动作与奖励

- **动作**：1个离散分支，大小8，即候选槽位。不存在、不可达的槽位被遮罩。全被遮罩时回合以`NoCandidate`结束，并单独计数（这说明执行器标定或提取有问题，不是策略的问题）。
- **奖励**：
  - 到达终点+1；
  - 每次站上新的、更高的支撑+0.1（沿用现有进展奖励的定义，即同一支撑只付一次）；
  - 每个option −0.01；
  - 执行器失败按类型−0.05（坠落到地面不结束回合，回到地面重新选择）。
- **回合上限**：20个option或60s模拟时间。

## 3. 底层：通用执行器

### 3.1 现有控制器的可复用部分

| 部件 | 来源 | 复用方式 |
|---|---|---|
| `Hold(desiredTorso)`：以躯干坐标期望位姿给已抓手下目标，而非世界目标 | `BoxClimbSmokeController.Hold`、`ClimberScriptController.HoldSupport` | **原样复用**。【数据】两级台阶16/16、横档墙均依赖它；它避免跟随并抵消yaw偏差 |
| 三段式伸手：先撤到边外侧0.2m并抬高0.1m，再前移，最后落手 | `BoxClimbSmokeController` Seek的approach[0..2]、`ClimberScriptController.Reach` | **复用逻辑，坐标泛化**：硬编码的`front±0.2`、`top+0.1`改为边坐标系中的偏移 |
| 抓握门槛：到达阶段2且距抓点<0.04m才请求抓握 | 同上 | 原样复用 |
| 撑起：先期望躯干在边前`top+0.53`；躯干越过`top+0.43`后转为向内`inward` | Press阶段 | **复用结构**，inward由d_stand计算（目前两级台阶固定0.30，单箱0.55） |
| 释放与重新武装：双手false，等待0.35s | Release阶段 | 原样复用。它满足身体的false→true重新武装和冷却规则 |
| 悬挂换手：一手Hold，另一手SeekGrab上一根，抓稳后松开旧手 | `ClimberScriptController` rung循环 | **复用**作为`hang`类边的过渡原语 |
| 成功判定 | 两级台阶用手写条件 | **替换**为Agent的`TrySupport`加速度阈值，与一级/二级登层判定一致 |

### 3.2 需要泛化的部分

1. **边坐标系**：原点在区间中心，x沿边，z为内法线，y为场地up。现有控制器隐含"边朝+z、在躯干正前方、x=±0.3"。
2. **双手间距**：固定±0.3m，改为在可抓区间内取间距min(0.6, 区间长度−0.1)。区间<0.30m时只用单手（需另外验证单手撑起是否可行，阶段B中单列）。
3. **起始站位**：现有控制器假设躯干正对目标边、距离约0.4m。身体没有行走能力（只有躯干和两只手），所以：
   - 可达性过滤（§2.1第5步）必须把"无需移动即可伸到"当作硬约束；
   - 侧向移动只能通过"抓住当前边并沿边换手"完成，作为可选原语`traverse`，放在第二批。
4. **朝向**：躯干Y轴旋转未锁定，`LockRotationY=false`（`ClimberBody.cs:42`）。但没有直接的转向命令，现有控制器都只处理正前方的边。侧边、背面的边先由ψ_max过滤掉；能否用双手不对称拉力转身，留作标定实验的一项。
5. **撑起参数**：`top+0.53/0.43`和`inward`取自固定箱型。泛化时它们依赖边高、d_stand和上方净空（悬挑下方的翻越高度可能不足）。
6. **失败检测与返回**：现有控制器只有60s超时和坠落。执行器需要分类上报：
   - `GripTimeout`：伸手超过4s未抓上；
   - `PullStall`：撑起阶段2s内躯干升高<2cm；
   - `Fall`；
   - `Slip`：抓握断裂；
   - `Timeout`：单个option超过10s。
   - 上报后进入安全状态：有抓握则保持，否则松手落地。

### 3.3 最可能失败的几何情况（按风险从高到低）

| # | 几何 | 为什么会失败 | 现有证据 |
|---|---|---|---|
| 1 | **窄台阶**：下一层就在当前边后方，d_stand<0.45m | 无法翻上去站住；需要直接从悬挂转到更高的边，现有箱子控制器没有这条路径 | 【数据】Standard堆叠层间z偏移只有0.05–0.15m，Hard为0.15–0.30m（`BoxStackGenerator.Generate`）；两级台阶的落脚深度为0.6m |
| 2 | **悬挑**：上层伸出下层0.125–0.40m | 伸手路径从下方或外侧上抬时会撞到悬挑底面；翻越时没有脚，躯干被顶在悬挑下方 | 【数据】Hard悬挑2–3个，最大0.40m（[BOX_STACK_ACCEPTANCE.md](BOX_STACK_ACCEPTANCE.md)特征表）；执行器在这类几何上未测过 |
| 3 | **边不正对躯干**（侧边、斜放的箱） | 没有转向命令；Hold时的yaw扰动会累积 | 【推断】现有两级台阶测试只覆盖0/±15°场地旋转，是整体旋转，不是边相对躯干旋转 |
| 4 | **间隙与侧塔**：0.10–0.40m宽 | 躯干宽0.6m，跨越时可能卡进间隙；伸手越过间隙后拉升方向不在正前方 | 【数据】Hard间隙0.20–0.40m；未测 |
| 5 | **短边或部分被遮挡的边**（<0.6m可抓区间） | 双手间距不足；单手撑起未验证 | 【数据】身体拒绝0.12m窄缝、允许0.30m净空（BOX_STACK_ACCEPTANCE身体准入测试） |
| 6 | **超出验证范围的升高**（>1.05m）或升高过小（<0.20m） | 过高够不到；过低时三段式伸手的"抬高越过边"阶段可能与躯干冲突 | 【数据】横档墙高差0.15–0.25m、横距小时多为0/8（LAYER2_SOLVABILITY） |
| 7 | **平接缝被误判为唇沿** | 选中后执行器试图翻越平地 | 【推断】由§2.1第3步的落差判据处理；需要单元测试覆盖 |
| 8 | 玩家结构中的**动态箱** | 身体对动态箱返回`DynamicDeferred`，不抓（`ClimberBody.cs:147`） | 范围外：迁移评估只使用静态化加载的结构，与现有加载器相同 |

## 4. 研究问题如何保持

- **研究问题**：在程序化结构上训练的高层路线策略，能否在玩家搭建的结构上选对路线？
  - 这仍是迁移问题，只是迁移的对象从"运动技能"换成了"路线选择"。
  - 底层是固定的通用执行器，它在两类结构上的成功率要单独测量，不计入策略的功劳。
- **训练分布**：`BoxStackGenerator` Easy/Standard/Hard（按种子划分训练集和留出集，不按执行器成功率筛选，沿用生成器规则）。
- **测试分布**：
  - 玩家搭建的结构。
  - 当前没有运行时搭建UI（[BOX_STACK_ACCEPTANCE.md](BOX_STACK_ACCEPTANCE.md)"本轮未实现运行时搭建UI"）。
  - 在UI完成前，先用手工编写的结构JSON作为代理测试集，并显式标注它是代理。
- **对照**：同一执行器下的四种高层：
  1. 随机可达候选；
  2. 贪心，选Δh最大的可达候选；
  3. **神谕规划器**：在候选图上做最短路径，边代价为阶段B标定出的执行器失败率；
  4. PPO高层。
- **结果拆解**：
  - 每回合分为"路线错误"（选了不通向终点的边，或代价明显更高的边）和"执行失败"（执行器在正确的边上失败）。
  - 路线质量用相对神谕的regret衡量。
- **关键风险**（【推断】）：如果贪心或神谕规划器已经在所有结构上接近执行器上限，高层RL就没有必要存在，研究问题也就没有区分度。验证方法：
  - 阶段C先测对照1–3。
  - 只有当它们之间、以及它们与执行器上限之间存在明显差距时，才训练PPO。
  - 预期差距来自：结构几何使执行器成功率出现非单调变化（例如更高的边反而更好翻），以及死路（贪心爬上去后没有下一条可达边）。
- **与端到端线的衔接**：执行器的单个原语（例如S1b→一级撑起）以后可以逐个替换为学习得到的技能，在同一高层下比较。

## 5. 工作量与分阶段验收

工作量为开发时间估计，不含排队等待；训练按现有CPU吞吐估计（5M步约32–34分钟/种子，`docs/data/climb-demo-init/runs/*/timing.jsonl`）。每个阶段结束都按AGENTS.md汇报，并经确认后再进入下一阶段。

| 阶段 | 内容 | 估计 | 验收标准 |
|---|---|---|---|
| A 候选提取 | 顶边区间、唇沿、d_stand、可达过滤（阈值先取保守值）；Editor脚本生成可视化场景 | 2–3天 | ① 单元测试覆盖：旋转箱、平接缝、部分遮挡、悬挑、窄台阶<br>② 在59个box-stacks和两个冒烟关卡上，候选区间采样点与`ClimberBody.GetGripCandidate`的合法性判断100%一致（手放到采样点时）<br>③ 地面起点到终点在候选图上连通的结构比例，与`BoxStackGeometry.MinimumTransitions`的粗图逐个对照，差异逐条解释 |
| B 通用执行器 | 边坐标系下的mantle / hang / release原语、失败分类；先不做traverse | 5–8天 | ① 回归：单Tall箱16/16、两级台阶16/16（不低于现有专家）<br>② 标定扫描：在参数化单步关卡（Δh、ρ、ψ、d_stand、悬挑网格）各8个变体上测成功率，产出可达阈值表<br>③ 在59个堆叠的全部"单步转换"上报告成功率和失败分类。不设通过门槛，结果用于§2.1第5步的阈值和神谕代价 |
| C 规划对照 | 随机、贪心、神谕三种高层，在同一执行器上跑完整关卡 | 2天 | ① Easy上神谕的成功率≥执行器单步成功率之积的预测值（检验执行器标定是否自洽）<br>② 三者在训练集、留出集上的成功率和regret表；据此决定是否进入D（见§4关键风险） |
| D 高层RL | 事件触发决策的Agent、动作遮罩、上述观察和奖励；先用脚本化高层证明环境可解，再训练 | 3–4天开发，加训练（2种子） | ① 脚本化高层（=神谕）在新环境中的成功率与C一致<br>② PPO在留出程序化结构上的成功率高于贪心，regret低于随机，两个种子方向一致 |
| E 迁移评估 | 代理玩家结构集（手工JSON，≥20个，覆盖§3.3的几何类型），之后换成UI搭建的结构 | 3–5天（不含搭建UI） | ① 报告PPO、贪心、神谕在代理集上的成功率，拆分路线错误与执行失败<br>② 按几何类型分组报告 |

- 合计约3–4周开发时间。
- 最大的不确定性在阶段B：§3.3的第1、2项可能需要新的运动原语。若阶段B标定显示窄台阶或悬挑的成功率接近0，先汇报，再决定是扩展执行器，还是在训练和测试分布中把它们标为"执行器不支持"（必须同时在两类分布上一致地标注，不能只从测试集里删掉）。
